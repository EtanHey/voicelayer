# 2.4 automated flow gate

On the occupied M4, run only isolated socket/unit and offscreen checks:

```sh
bash scripts/e2e-2.4.sh --swift --report docs.local/E-E2E-SUITE/run.json
```

Bun loads the repository preload. Functional subprocess cases have a 30-second
scheduling budget; the shared 900-second deadline includes compilation and locks.
Reports refuse to overwrite. The inventory names exact Swift methods and the
runner fails if a declared method did not execute. Generate/check it with:

```sh
python3 scripts/generate-e2e-2.4-coverage.py
python3 scripts/generate-e2e-2.4-coverage.py --check
```

[Coverage and separate formal/artifact prerequisites](e2e-2.4-coverage.md) list all
six former Swift skips. They are excluded from this functional gate, not counted
as passes. The formal History replay stays in `formal/speech-queue/check.sh`.
All six separate cases can run on the M1 with their listed producer or opt-in flag.

On the M1 rig, through the lead's admission:

```sh
bash scripts/voicebar-ui-e2e.sh --scenario e2e24 --output "$PWD/.build.noindex/e2e24-native"
```

This uses the existing QA builder, boundary broker, recorder, supervisor and
exporter. Every native case has an `e2e24:<case>` surface and timing attachment.
Missing providers produce owner-labelled skip receipts and later cases continue.
The REVIEW-813 fixture contract is assigned to lanes A/B. Settings controls are
queried in Settings; local actions assert resulting state. Socket controls use
production commands, with synthetic daemon state responses in the QA host.

Import guarded M1 results:

```sh
bash scripts/e2e-2.4.sh --swift --release --native-output /path/to/e2e24-native --report docs.local/E-E2E-SUITE/release.json
```

Only verified per-case surfaces upgrade their mapped rows. A partial native run
can show the individual cases it completed. Physical F5, real terminal insertion,
installed update/restore, mute audio exclusion and NarrationLayer transport stay
`UNPROVED-native` until native/runtime cases exist. Thus current coverage cannot
produce releaseReady=true; that is an explicit coverage gap, not a permanent skip.
Missing/failed receipts, skips and local plus native recording time over 900 seconds
also refuse readiness. The lead must verify candidate provenance independently.
D11 still requires an M1 timing run, including build/preflight, before any claim
that the complete gate takes 15 minutes. The recording interval excludes that setup.

The M4 display fixture includes model, scale, CG display mode and UTC capture from
`swift scripts/e2e-2.4-screen-probe.swift`. M1 geometry/model/date come from REVIEW-813;
its scale is labelled nominal, not independently re-probed by this worker.
`E2E24MeasuredGeometryTests` renders both fixtures through production notch layout,
measures full wing-control content bounds against the physical housing gap and
asserts at least 8 pt clearance. Glass intentionally tucks under the housing; it
is not a control. PNGs are in `.build.noindex/e2e24-geometry/`.

`verify-notch-event-handling.sh` launches/drives a QA app. It is intentionally not
run on the occupied M4. The lead may run that existing acceptance script with an
isolated QA bundle on M1 alongside D11. No substitute native UI driver is added.

Existing runtime receipts can be attached with repeated, quoted row mappings:

```sh
bash scripts/e2e-2.4.sh --swift --release --native-output /path/to/e2e24-native \
  --candidate-app /path/to/candidate.noindex/VoiceBar.app \
  --attest 'F5 physical gestures=/path/to/t3-proof.json' \
  --report docs.local/E-E2E-SUITE/release-attested.json
```

The candidate is read only. Its Info.plist GitCommit must equal the checkout HEAD;
its digest comes from the existing T3 bundle-digest implementation. Every receipt
must be newer than the build, at most 24 hours old, and no more than five minutes
in the future. T3 v2 receipts go through `t3-optf5-proof.ts check` against that
bundle. They prove Option+F5 only, so the broader physical-gesture row remains
unproved until tap, hold, lock and hint timing have a real producer too.

Other receipts use [the v1 schema](../tests/fixtures/e2e-2.4/attestation.schema.json).
Evidence paths resolve beneath the receipt directory and their SHA256 values
must match the files. The producer must exist in this repository and be registered
for that complete row in `ATTEST_PRODUCERS`. There are currently no registered
producers: valid schema alone never upgrades a row. Installer harness completion
is synthetic and cannot prove a real install/restore; release verification scripts
reuse the T3 proof. Missing producers for all five rows are explicit follow-ups,
not waivers. Invalid attestations fail before tests start. Reports retain validated
receipt path, digest, schema, timestamp and the exact remaining proof limitation.

Native per-case attachments are retained as `UIE2E-E2E24-TIMING-<case>` and exported
to `timings.json` with each duration and a total. Missing, duplicate, unsafe or
invalid timings fail the native report. Settings cases click and restore remaining
safe controls; unsupported unexercised controls fail explicitly. Execution of these
new Settings interactions remains M1-pending until the lead runs the native suite.
